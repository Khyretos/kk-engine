# BUGS.md — Kreative Kompas Engine bug tracker

**Read this before starting any debugging session, and before saying "this
works" about anything below.** This file exists because bugs were getting
rediscovered across sessions — a fix landed in one module, the same root
cause resurfaced in a sibling module weeks later, and nothing pointed back
to the original fix or explained why. `README.md`'s own "Known
simplifications" section had already gone stale in-session (it still
claimed RmlUi image loading was "a stub" hours after that was fixed, and
claimed resize handling was fully verified before a real panel-scaling bug
was found in that exact area) — a long narrative changelog is not a
substitute for a queryable table. This is that table.

## How to use this file

- **Before fixing a bug, search this file for the symptom, the file, or
  the general area first.** If it's listed as Fixed, the bug you're
  looking at is either a regression (worth its own new entry linking
  back) or a *different* bug with a similar symptom — don't assume
  it's already handled just because something with this name exists.
- **When you fix a bug, add or update its row here in the same
  session**, not as a follow-up. Include enough in "Root cause" and
  "Fix" that someone (human or AI) hitting a similar symptom in a
  *different* module can recognize the same pattern without re-deriving
  it from scratch.
- **When you find a bug you don't fix yet**, add it anyway with
  Status = Open. An accurately-described open bug is more valuable
  than a silent gap.
- IDs are `BUG-NNN`, assigned sequentially, never reused even if a bug
  turns out to be invalid — so a stale reference in old commit messages
  or old conversation history still resolves to the right row.
- "Session" is the rough chronological point this was found, for
  cross-referencing against README's own "Immediate next slices"
  history if the fuller narrative is ever needed. Not a hard date.

| BUG-001 | RmlUi / MarketplaceUiModule | Marketplace card text (game titles, descriptions) not rendering / laying out incorrectly. | RmlUi has no built-in "p/div default to block" behavior the way HTML does — `display:block` was missing from every `<p>`/`<div>` in the generated RML. | Added explicit `display:block` to every block-level element in the generated RML string. | Early (pre-transcript-summary) |
| BUG-002 | RmlUi / RmlVulkanRenderInterface | RmlUi debugger's "Outlines" panel crashed the app. | Three compounding GPU resource-lifetime bugs: (1) `ReleaseGeometry()`/`ReleaseTexture()` destroyed GPU resources immediately with no GPU-idle check — Outlines churns far more temporary geometry per frame than normal content, making the race likely; (2) `Application::~Application()` ran module `shutdown()` before the renderer's own `vkDeviceWaitIdle()` ever fired; (3) fixing #1 with a deferred-deletion queue then leaked pending texture deletions past process exit on a fast shutdown. | (1) `PendingDeletion` queue in `beginFrame()`, freed after `kDeletionDelayFrames=3`; (2) explicit `vkDeviceWaitIdle()` at the start of `Application::~Application()`; (3) drain remaining pending deletions in `~RmlVulkanRenderInterface()`, safe because fix #2 guarantees GPU idle by then. | Session: RmlUi debugger work |
| BUG-003 | Physics / plasticity verification | Plasticity diagnostic showed no change, looked like plasticity wasn't working. | Was reading the wrong signal — `FmGetVertRestPosition()` checks *rest* positions, which never change; FEMFX tracks plastic deformation internally with no public accessor for it directly. | Switched the diagnostic to measure real vertex-to-vertex distance (started at 1.0, tracked over time) instead — the correct, working signal. | Session: plasticity verification |

| BUG-005 | Physics / PhysicsModule scene setup | Spawning many (dozens of) physics objects caused them to fall through the ground plane. | `kMaxObjects` was raised from 8 to 64 in an earlier session, but the related FEMFX scene capacity parameters (`maxDistanceContacts`, `maxVolumeContacts`, `maxBroadPhasePairs`, `maxDeformationConstraints`) were left hardcoded at the *old*, much smaller values. With real object counts, the actual contact count exceeded these fixed limits, and a contact FEMFX has no room to record gets no real collision response. | Scaled all of these to a generous multiple of `kMaxObjects` instead of another fixed number. | Session: physics scale/scenes |
| BUG-006 | Physics / PhysicsModule rendering | Physics-spawned tetrahedra looked "hollow" — a smooth, iridescent-looking gradient instead of sharp, distinct flat faces. | The render bridge shared vertices between adjacent triangular faces and averaged their normals together — correct for genuinely high-poly curved meshes, wrong for a 4-faced tetrahedron where it blends each face's shading into its neighbors. | Restructured to real flat shading: `numTets * 12` unique per-face vertices (4 faces × 3 corners, none shared), each with its own single, correctly-computed face normal. | Session: physics rendering fix |
| BUG-007 | Physics / PhysicsModule "Spawn fracturable cube" | Fracture only ever produced 1-2 pieces — didn't look like real breaking. | A single 6-tet cube has too few internal boundaries for fracture to separate it into more than a couple of pieces. | Replaced with a real 2×2×2 grid of connected cube-cells (48 tets), later generalized into `buildGridBox()` for arbitrary shapes. | Session: physics scale/scenes |
| BUG-008 | Physics / PhysicsModule "Spawn fracturable cube" | Selecting a different material in the Material Grid never changed how the fracturable cube broke. | The button used a single hardcoded `Material`, completely ignoring `m_selectedMaterial`. | Changed to use `m_selectedMaterial`. | Session: physics scale/scenes |
| BUG-009 | Physics / MaterialGridModule presets | Every material behaved as effectively unbreakable regardless of selection. | `fractureStressThreshold` values (3e5 to 5e8) were carried over from AMD's own reference material examples, but this project's actual simulated stress magnitudes run orders of magnitude smaller. None of the preset values were ever reachable by any real impact this demo produces. | First retuning pass: rescaled thresholds into a working order of magnitude, linearly scaled by each material's own stiffness. **Superseded by BUG-020** — that scaling heuristic itself turned out to be the wrong mental model. | Session: physics scale/scenes (first pass); see BUG-020 for the correct fix |
| BUG-010 | Rendering / shadow.vert | Shadows stopped working entirely — every fragment read as fully lit, no shadow anywhere in the scene, on both `kke_demo` and `physics_demo`. | `shadow.vert` still declared only 3 vertex attributes (position/color/normal) from before `Vertex` grew a 4th field (`uv`) for material-texture work in an earlier session. The shadow pipeline's vertex input state is always built from `Vertex::attributeDescriptions()` (4 attributes), so there was a real mismatch between what the pipeline described and what the shader consumed — invisible to Vulkan validation (unused pipeline attributes aren't strictly invalid), but caused a silent geometry-submission failure on this project's software rasterizer. Found via a genuinely exhaustive diagnostic chain that first ruled out the light-space matrix, the UBO layout, `textureSize()`, and the new `PhysicsModule::renderShadow()` code before finally sampling the shadow map's own stored depth and finding it stuck at the clear value. | Added the missing `uv` attribute declaration to `shadow.vert` (unused in the shader body, but matching the pipeline's real vertex input state). | Session: shadow regression investigation |
| BUG-011 | RmlUi / UiModule slider interaction | `<input type="range">` sliders could not be dragged — clicking could jump the value once, but holding and moving the mouse afterward did nothing. | `WidgetSlider::ProcessEvent` internally checks `event.GetTargetElement() == track`, but the slidertrack/sliderbar children are added as non-DOM elements (confirmed by reading RmlUi's own `WidgetSlider.cpp`/`Element.cpp`) — that check can never succeed, so the widget never responds to real mouse events at all, click or drag. | Bypassed RmlUi's internal widget entirely: on mousedown over an `input.range`, compute and `SetValue()` the new value directly from mouse X; track a "currently dragging" element and repeat the same computation on every subsequent mousemove until mouseup. | Earlier session (click fix) + this session (drag fix) |

| BUG-020 | Physics / material toughness ordering | Selecting "Rubber" and dropping a fracturable object shattered it (45-58 pieces), while "Iron" under the identical drop stayed intact — backwards from real-world intuition (rubber should be tougher/bouncier, iron should be tougher/dent-not-shatter) and backwards from the relative `fractureStressThreshold` values the two materials had been given. | The first retuning pass (BUG-009) assumed stress scales linearly with a material's own stiffness, so it scaled every threshold by stiffness. Reading FEMFX's own source (`FEMFXUpdateTetState.cpp`) showed stress is actually computed as `stiffness_matrix * displacement` — since softer materials also *deform more* under the same impact, the net relationship between stiffness and real stress is not a simple linear scaling, and the two effects can partially cancel or even reverse depending on the specific impact dynamics. | Added a temporary diagnostic directly into FEMFX's own fracture-check code (`FEMFXUpdateTetState.cpp` — no public API exposes `maxStressEigenvalue`) and measured real stress ranges for all five materials under the identical standard impact: Rubber ~1,200-8,450; Wood ~1,483-22,485; Stone ~2,386-52,794; Glass ~4,719-36,640; Iron ~6,690-314,820. Retuned every threshold relative to its own material's real measured range instead of a shared formula. Verified by repeated real testing: Glass → 13 pieces, Iron → 9-11 pieces (tougher, correct direction), Rubber → zero fracture (genuinely bounces intact). The temporary FEMFX diagnostic was fully removed afterward (confirmed via a repo-wide search). | Session: material toughness root-cause |
